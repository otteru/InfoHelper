# RAG 평가 데이터셋과 실험

InfoHelper의 채용 공고 검색 품질을 측정하고 개선하기 위한 데이터셋과 실험 코드다.
직행 IT·개발 공고를 수집하고, 여러 검색 방식의 결과를 모아 관련도를 판정한 뒤 평가용 정답 데이터(qrels)를 구성한다.
평가 데이터와 임베딩은 운영 서비스 데이터와 분리해 관리한다.

최종 평가용 라벨은 [`dataset/labeling/pool_v1/`](dataset/labeling/pool_v1/)에서 확인한다.
데이터 구성을 확인하려면 아래 설명을, 판정 기준을 확인하려면 [라벨링 가이드](../docs/labeling-guidelines.md)를 먼저 읽는다.
수집·임베딩·검색·라벨링 도구의 실행 방법은 각 폴더의 README에서 안내한다.

## 폴더 구조

```text
RAG_evaluation/
├── README.md
├── crawler/       # 평가용 채용 공고 수집 코드
├── dataset/       # corpus·쿼리·라벨 및 데이터셋 구성 기록
│   ├── corpus.jsonl            # 정제된 평가 공고 4,681건
│   ├── queries/                # 평가 쿼리 80개
│   ├── zighang/                # 수집 원본·체크포인트 (Git 제외)
│   └── labeling/
│       ├── pilot_aligned_v1/
│       ├── pilot_aligned_v2/
│       └── pool_v1/             # 최종 평가용 라벨 3,022쌍
├── embedding/     # 평가 corpus의 청킹·임베딩과 실험 설정 관리
├── retrieval/     # Dense·BM25·Hybrid 검색 결과 생성
├── labeling/      # 사람이 라벨을 입력·검수하고 결과를 내보내는 보조 도구
└── artifacts/     # 검색 결과·실험 설정·중간 판정·작업용 DB (Git 제외)
```

위 트리는 주요 경로만 표시한다. 로컬 생성 파일은 저장소를 내려받았을 때 없을 수 있다.

| 경로 | 역할 | 상세 안내 |
| --- | --- | --- |
| `crawler/` | 직행 목록·상세 API에서 공고를 수집하고 체크포인트로 재개한다. | [수집 방법과 한계](crawler/README.md) |
| `dataset/` | 평가 입력과 확정 라벨을 모으는 위치다. 데이터 구성·라벨링 과정의 공개 자료도 이곳에 정리한다. | 아래 데이터셋 설명 |
| `embedding/` | 평가 전용 DB 테이블에 원문·실험 설정·청크와 벡터를 저장한다. | [임베딩 실행과 재개](embedding/README.md) |
| `retrieval/` | 같은 corpus·쿼리로 Dense, BM25, 저장된 결과 기반 Hybrid(RRF)를 실행한다. | [검색 방식과 산출물](retrieval/README.md) |
| `labeling/` | 파일럿·holdout 판정, 불일치 합의, AI 판정 검수와 내보내기를 지원한다. | [로컬 라벨링 도구](labeling/README.md) |
| `artifacts/` | 검색 run·manifest, 표본 스냅샷, AI 판정과 SQLite 이력 등 작업 산출물을 보관한다. | Git 제외 대상 |

## 데이터셋 구성

- **Corpus**: 수집한 공고 5,000건에서 50자 미만 본문과 동일한 `title + content`를 정리한 4,681건이다. 원문뿐 아니라 직행이 제공한 요약도 포함한다.
- **쿼리**: 총 80개이며 Keyword 12, Semantic 16, Constraint-heavy 20, Entity-heavy 16, Ambiguous 8, No-match 8개로 구성한다.
- **판정 후보(pool)**: 쿼리별 Dense·BM25 top 20을 합쳐 중복을 제거한 3,022개의 쿼리–공고 쌍이다. 현재 저장된 두 검색 결과를 결합하는 Hybrid는 이 합집합에 새 공고를 추가하지 않는다.
- **관련도(qrels)**: 쿼리와 공고 사이의 관련도를 0·1·2로 기록한다. 보류·미평가를 0점으로 간주하지 않는다. 세부 조건과 예외는 [라벨링 가이드](../docs/labeling-guidelines.md)를 따른다.

현재 평가용 합본은 **`pool_v1`**이다. 80쿼리의 3,022쌍이며 점수 분포는 0점 2,051 / 1점 196 / 2점 775다.

| 파일 | 내용 |
| --- | --- |
| [judgments.jsonl](dataset/labeling/pool_v1/judgments.jsonl) | 쿼리·공고 ID, 쿼리 문자열, 점수, 판정 출처, 버전과 기준일 |
| [qrels.txt](dataset/labeling/pool_v1/qrels.txt) | `query_id 0 doc_id score` 형식의 평가용 관련도 |
| [manifest.json](dataset/labeling/pool_v1/manifest.json) | 건수·분포·출처별 집계·입력 해시·합본 해시와 반영 범위 |

| 판정 출처 | 건수 |
| --- | ---: |
| 파일럿 사람 확정 | 120 |
| holdout 최초 사람 판정 | 120 |
| 검수 사람 판정 | 129 |
| 검수 에이전트 판정 | 224 |
| Grok 1차 자동 통과 | 2,429 |

사람과 AI 판정을 합친 데이터이며, 사람 전수 확정 데이터가 아니다.
`judgments.jsonl`에는 공고 본문이나 개별 판단 근거·전체 변경 이력이 들어 있지 않다.
파일럿의 상세 판정 기록은 `dataset/labeling/pilot_aligned_v2/`에 보존하며, 그 외 작업 이력은 로컬 `artifacts/`에 남아 있다.

반영 범위:

- 자동 통과 50건은 화면에서 확인했지만 점수를 저장하지 않아 합본에 반영하지 않았다(`audit_50_applied: false`).
- holdout은 합의 DB가 아닌 최초 사람 점수를 사용한다. 이후 합의로 최초 비교 일치율을 다시 계산하지 않는다.
- 각 행의 `guideline_version: 1.4`는 합본에 기록된 기준 버전이다. 새 R7 규칙은 검수 에이전트 224건에 적용했으며, 파일럿·holdout 등을 모두 v1.4로 재채점한 것은 아니다.
- 평가 입력은 `dataset/corpus.jsonl`과 `dataset/queries/eval_queries_80.jsonl`이다. 쿼리 CSV는 열람용으로 함께 제공한다.
- `dataset/zighang/`의 수집 원본·체크포인트와 `artifacts/`는 Git 제외 대상이다. 검색 재실행에는 평가 DB·모델 API 설정이 필요하며, 합본 재생성에는 로컬 판정 DB 등 중간 산출물이 추가로 필요하다.

## 데이터 생성과 검수 흐름

1. **수집·정제**: 채용 공고를 수집하고 정보가 부족한 본문과 중복 문서를 정리한다.
2. **임베딩·검색**: 기준 실험으로 본문을 1,000자씩 청킹하고 Qwen3 Embedding 8B의 1,536차원 벡터를 생성한다. Dense·BM25 검색 결과를 모아 판정 후보를 고정한다.
3. **파일럿 120쌍**: 사람과 독립 AI 판정을 비교하고 불일치 사례를 통해 기준을 정리한다.
4. **Holdout 120쌍**: 파일럿과 겹치지 않는 표본으로 기준 적용을 확인한다. 최초 비교 결과와 이후 합의 결과는 분리해 보존한다.
5. **나머지 2,782쌍**: Grok으로 1차 판정을 생성하고, 검수 후보 353쌍을 사람 129건·에이전트 224건으로 나누어 검수했다. 자동 통과 50쌍은 화면 확인만 했으며 저장된 감사 결과는 없다.
6. **최종 데이터 정리**: 판정 출처를 구분해 `pool_v1`의 qrels·판정 목록·manifest를 생성했다.

검수 대상으로 표시된 AI 1차 판정은 검수 결과로 대체하고, 자동 통과분은 출처를 표시해 합본에 포함했다.
평가 기준일은 **2026-09-07**로 고정하며, 재실행 날짜에 따라 시간 조건을 바꾸지 않는다.

## 라벨링 도구와 산출물 관리

`labeling/`은 데이터셋 제작을 돕는 로컬 보조 도구다. 파일럿·합의 등 특정 단계용 화면과 스크립트도 포함하며,
데이터셋의 구성과 품질을 이해하기 위해 모든 도구 코드를 읽을 필요는 없다.
일부 도구는 로컬 파일과 과거 단계의 산출물에 의존하므로 실행 전 해당 README와 입력 경로를 확인한다.

`artifacts/`는 Git에서 제외한다. 공개 합본의 manifest에 입력 해시와 반영 범위를 기록한다.
작업용 DB와 중간 파일은 상세 이력 확인과 재생성에 필요하므로 로컬에 보존한다.

## 실행 안내

프로젝트 루트에서 Miniconda 환경을 활성화한 뒤 각 단계의 README를 따른다.

```bash
conda activate infohelper
```

수집은 외부 API, Dense 검색과 임베딩은 평가용 Supabase 및 모델 API 설정이 필요하다.
기존 데이터셋으로 평가할 때는 corpus와 쿼리 버전·해시를 유지한다. 채용 공고는 변하므로 새로 수집한 결과가 기존 평가 입력과 같다고 가정하지 않는다.
