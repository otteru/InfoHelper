# InfoHelper 채용 검색 라벨링 기준과 합의 기록

버전 1.4 · 합의 기록일 2026-09-17 · 평가 시간 기준 2026-09-07

## 1. 목적과 현재 상태

다른 세션의 사람·에이전트가 같은 질문–공고 쌍을 같은 기준으로 평가하도록 만든 기준 문서다. 판단 대상은 저장된 공고의 질문 관련도이며, 지원자 채용 여부나 기업의 우열을 평가하지 않는다.

현재 데이터는 `RAG_evaluation/dataset/labeling/pilot_aligned_v2/pairs.jsonl`이다. 한 행에 질문·공고 전체·0/1/2점·근거·판정 출처가 함께 있다. 제안 상태였던 17건은 `/confirm`에서 사용자가 확정했다. 이전 제안 스냅샷은 `pilot_aligned_v1`에 보존한다.

120건의 현재 상태는 최초 사람·에이전트 점수 일치 93건, 사용자 확정 27건이다. 모든 점수가 사용자 최종 확정이지만, 93건은 새 기준으로 전수 재검토한 것이 아니며 최초 에이전트의 검토 요청도 보존한다.

## 2. 점수와 판정 순서

사용자는 처음 요청한 ‘0~1’이 오타라고 정정했다. 점수는 **0·1·2**를 그대로 사용하며 확률이나 0~1 정규화 값이 아니다.

| 점수 | 의미 | 판정 예 |
|---|---|---|
| 2 | 질문의 핵심 업무와 요구 조건에 적합 | 백엔드 채용에 백엔드 아키텍처 설계가 핵심인 공고 |
| 1 | 부분 관련: 실제 관련 업무는 있으나 부수 역할이거나 일부 조건의 근거 부족 | 인프라 FDE 업무에 보안 정책 구현이 일부 포함 |
| 0 | 핵심 의도·기술·직무 근거가 없거나 명시 조건을 위반 | SAP ABAP 질문에 네트워크 운영 공고 |

1. 질문에서 핵심 직무·기술·회사와 지역·경력·시간 등의 조건을 구분한다.
2. 공고 제목·본문·메타데이터를 함께 읽고 각 조건을 ‘확인됨 / 위반 / 미확인 / 충돌’로 구분한다.
3. 핵심 업무 자체가 다른지, 같은 업무가 부수적으로 포함된 것인지 판단한다.
4. 명시 조건 위반은 0, 핵심 업무는 맞지만 부가 조건 미확인은 일반적으로 1을 적용한다.
5. 아래 확정 사례가 있으면 해당 사례의 사용자 판정이 우선한다. 일반화하기 어려운 부분은 예외로 남긴다.

‘없음’은 저장된 평가 근거에 없다는 뜻이다. 실제 회사에서 그 일을 절대 하지 않는다는 단정이 아니다. 직무 전체가 짧거나 충돌해 판단이 어려우면 점수와 별개로 검토 필요 상태를 남긴다. 미평가·보류를 0점으로 변환하지 않는다.

## 3. 합의로 확정한 규칙

### R1. 주요 업무와 부수 업무

질문이 특정 일을 찾으면 그 일이 해당 역할의 중심인지 확인한다. 단지 ‘주요업무’ 항목 안에 한 번 나온다고 무조건 2가 아니다. 역할 설명, 책임 범위, 업무 전체의 목적을 함께 본다. 반대로 직무명이 다르다는 이유만으로 감점하지 않는다.

- Q068 보안 FDE: 보안 정책 구현은 실제로 포함되지만 인프라 배포·운영이 중심이다. 사용자 최종 **1**.
- Q013 Tech - Backend Engineer: 장애 대응·재발 방지 자동화가 명시돼도 서비스 개발 역할의 일부다. 사용자 최종 **1**.
- Q011 신한은행 아키텍트: 코어뱅킹 아키텍처·MSA 전환과 백엔드 설계·구현이 핵심이다. ‘백엔드 채용’은 구현 전담자로 한정하지 않는다. 사용자 최종 **2**.

사용자는 Q068에 대해 ‘온전히 fit 하다고 판단할 수 없다’면서도 부분적인 보안 업무를 보여주는 것은 타당하다고 설명했다. Q013도 해당 일이 메인이 아니라는 동일한 이유로 1을 선택했다. 이 기준은 직함 일치가 아닌 업무 중심성에 관한 것이다.

### R2. 핵심 기술·직무와 부가 조건의 구분

핵심 기술·직무를 다른 유사 단어로 대체하지 않는다. React는 React Native가 아니고, 서버관리는 서버 개발을 곧바로 뜻하지 않으며, AI라는 말만으로 생성형 AI·비전 AI를 보장하지 않는다. 예외로 **Java 질의는 Kotlin 공고를 포함할 수 있다.** 이 예외를 다른 언어 쌍으로 확대하지 않는다. **프리랜서는 계약직으로 본다.**

Q045 안랩 공고는 ‘신입만’의 해석 때문에 확정한 0이 아니다. 사용자는 ‘신입이 들어갈 수 있는 공고로 해석될 수 있다’고 하면서 **클라우드 VDI 근거가 없어서 0**이라고 결정했다. 신입·경력 공동 모집은 아래 R6로 1을 주며, 핵심 직무가 없으면 0이 우선한다.

핵심 업무가 확인되고 지역·근무 방식 등 부가 조건만 미확인이면 부분 관련 1을 제안할 수 있다. 다만 무엇이 핵심인지는 질문에 따라 달라진다. ‘정보보안기사’처럼 자격증 하나가 질문의 전부라면 자격증이 핵심이며 일반 보안 업무만으로 1을 부여하지 않는다.

- Q023 Team Lead Applied AI Engineering: 생성형 AI가 본문에 없어도 사용자는 Applied AI Engineer 역할이 생성형 AI를 암시한다고 보고 **1**. 일반 직무명 ‘AI’나 비전 AI 질의(Q043)까지 생성형 AI로 바꾸지는 않는다. 명시가 없어 2는 주지 않는다.
- holdout Q066 IT Manager: ‘AI 관련 일’에 SAP ERP 전환·IT 운영만 있으면 **0**. IT 관리만으로 AI 업무가 아니다.
- holdout Q001 Applied AI Architect: MLOps 질의에 모델 배포·LLM 경험은 있으나 MLOps 직무가 아니면 **1**.
- holdout Q033 금융사 운영: Java Spring 질의에 Kotlin·Spring·금융·서울이면 Java로 보고, 프리랜서는 계약직으로 봐 **2**.
- holdout Q041 인덕원 JAVA/GIS: 제목에 GIS가 있어도 근무지가 인천이 아니면 **0**. 지역은 필수 조건이다.

### R3. 경력은 지원 가능성을 중심으로 해석

사용자는 Q047의 ‘경력 8년 이상’을 **8년차가 지원 가능한 공고**로 해석하라고 명시했다. 공고 최소 연수가 반드시 8 이상이어야 한다는 해석을 적용하지 않는다. 7년 이상 모집은 8년차가 지원할 수 있다.

- Q047 Security Lead: 사용자 최종 **2**.
- Q030 경력 4년 이상 임베디드 질문에 신입 대상 공고: 사용자가 신입 대상임을 확인하고 **0**으로 확정.
- Q040 다직무 iOS: `경력무관(분야별 상이)`여도 ‘경력 3년 이상’은 **3년차가 지원 가능한 공고**로 해석한다. 사용자 최종 **2**.
- Q027 Modhaus Product Engineer: 직함에 시니어가 없어도 경력 구간이 시니어 지원 가능하고 분산 시스템 업무가 있으면 **2**.
- holdout Q027 Co-op intern: 질의는 시니어 **역할**이다. 체험형 인턴·Co-op는 시니어가 아니다. 경력무관은 ‘시니어가 지원 가능한 일반 공고’이지 인턴을 시니어로 보는 뜻이 아니다. **0**.

숫자 없는 ‘시니어’를 연차 구간 없이 모든 공고에 적용하는 규칙까지 합의했다고 표현하지 않는다. 새로운 경계 사례는 근거를 적고 판단을 요청한다.

### R4. 대기업은 채용 관점의 기업 범주

사용자는 법적 분류만을 고집하지 않고 **대기업·대형 테크를 취업 카테고리로 사용**하도록 지정했다. 예시 범위는 삼성·LG·SK·현대 등 대기업집단 계열사, 네이버·카카오·쿠팡 같은 대형 IT·플랫폼, 한국에 개발조직이 있는 글로벌 대기업이다. 직원 수만으로 판단하지 않는다.

기업 분류가 필요하면 잡코리아 등 채용사이트의 기업정보를 확인한다. 기업명, 분류, 출처 URL, 확인일과 가능하면 해당 분류의 기준일을 기록하고 사람과 모델에게 동일한 정보를 제공한다. 기업 규모에 대한 모델의 기억만으로 분류하지 않는다.

사용자가 제공한 법적 기업집단 설명은 이 카테고리의 배경이다. 이 문서는 그 법령·자산 기준의 최신 유효성을 검증한 법률 문서가 아니며, 숫자를 자동 분류 규칙으로 사용하지 않는다.

- Q067 코웨이 CAD/PLM PMO: 사용자 최종 **2**. 이번 값의 출처는 사용자 확정이며 별도의 기업정보 조회 결과를 꾸며 붙이지 않는다.
- Q067 PTKOREA 인턴: 사용자 최종 **0**. ‘대기업 개발’은 대기업 채용을 의미하므로 **대기업 고객의 프로젝트 수행만으로는 충족하지 않는다**.
- PTKOREA 사례를 모든 계열사나 모든 에이전시의 제외 규칙으로 확대하지 않는다. 직접 채용 기업의 분류와 고객 기업의 분류를 구분한다.

### R5. 날짜 경계

평가 기준일은 2026-09-07이고 ‘이번 달’은 2026년 9월이다. 다음 세션의 실제 날짜로 바꾸지 않는다. 게시 시점(`createdAt`)은 수집일과 구분한다.

- `X일 이전`은 그날 자체를 포함하지 않는다. 마감이 X일이면 조건을 위반한다.
- Q046 현대자동차 마감 2026-09-14: ‘9월 14일 이전’ 위반으로 **0**. 당일 제외는 이제 일반 규칙이다.
- `이번 달 마감`은 마감일이 2026-09인 공고다. 상시·채용시마감만 있고 9월 마감일이 없으면 충족하지 않는다.
- Q075 2020년 이전은 `createdAt` 기준이다. 2026년 게시면 **0**.

근무형태 충돌은 날짜 규칙과 별개다. Q042는 제목 교대근무와 본문 주간 근무가 충돌해 **1**. 제목 우선이나 본문 우선을 일반 규칙으로 두지 않는다. Q047은 재택 태그만으로 모든 하이브리드 조건을 충족한다고 확대하지 않는다.

### R6. 신입만은 전용 모집을 뜻한다

질의가 ‘신입만’ 또는 ‘경력직 말고 신입만’이면 신입 전용 여부를 본다. 일반 ‘신입’ 질의는 R3처럼 신입 지원 가능이면 된다.

- 신입 전용(경력 모집 없음)이고 다른 핵심 조건도 맞으면 **2**
- 신입도 되고 경력도 되는 공동 모집이면 **1**
- 경력만 받아 신입이 지원할 수 없으면 **0**
- 핵심 직무·기술이 없으면 신입 조건과 관계없이 **0**. Q045는 VDI 부재, Q034는 보안 QA 부재로 0이다. 공동 모집이라는 이유만으로 0을 준 것이 아니다.

### R7. 직무 질의와 기술 질의는 다르게 본다

2는 검색 결과에 반드시 나와야 하는 공고, 1은 한번 훑어볼 만한 공고, 0은 나오면 안 되는 공고다.

- **직무 질의**(백엔드, 프론트, AI 엔지니어 등): 그 일이 **메인**이어야 2. 있지만 메인이 아니면 1.
- **기술 질의**(React Native, Kubernetes, iOS, SAP ABAP 등): 그 기술을 실제로 쓰거나 요구하면 메인 직무가 아니어도 2.
- 둘 다 있으면(Java 백엔드): 기술 실사용 + 직무 메인 → 2. 기술은 있는데 직무가 부수 → 1. 기술 없음 → 0.

파일럿·holdout 120의 기존 점수는 이 규칙으로 다시 채점하지 않는다. 1차 검수 남은 224건에만 적용했다.

## 4. 합의 과정과 원점수 이력

1. Dense·BM25 top-20 합집합 3,022쌍에서 유형별 20쌍, 총 120쌍을 선정했다. 80개 질문을 모두 포함한다.
2. 사용자가 웹에서 120쌍을 평가했다. 최초 분포는 0점 71, 1점 11, 2점 38이다.
3. 대화 이력을 넘기지 않은 하위 에이전트가 같은 120쌍을 직접 읽었다. 사람 점수·메모는 제공하지 않았다. 별도 OpenRouter/Gemini 호출은 실행하지 않았다.
4. 93/120 일치(77.5%), 27건 불일치였다. 이 일치율은 정확도가 아니다. 사람에게는 intent·유형·해석 보기가 보였고 독립 에이전트에는 질문·공고만 제공돼 입력 조건 차이도 있었다.
5. 0↔2점 불일치 5건을 웹에서 사용자가 직접 합의했다.
6. 나머지 22건은 assistant가 합의 기준으로 재검토했다. 애매한 5건은 대화로 사용자에게 다시 확인했고, 17건은 제안으로 남긴 뒤 `/confirm`에서 사용자가 확정했다.

|---|---|---|---|

## 6. 애매한 사항을 처리하는 방법

- **기업 분류:** 외부 기업정보 사용은 허용됐지만 이번 세션에서 모든 기업을 실제 조회한 것은 아니다. 근거 없는 분류를 이미 확인된 사실처럼 저장하지 않는다.
- **정보 충돌:** Q042는 1로 확정했다. 다른 충돌이 발생하면 해당 조건의 중요도를 확인하고 근거 부족인지 판정 불가능인지 구분한다.
- **부분 관련과 핵심 부재:** 같은 직무의 부수 업무는 1을 줄 수 있지만 인접 산업·기술 이름만 겹치고 핵심이 없으면 0을 제안한다. 이 구분 자체가 애매하면 이유를 함께 남긴다.
- **모호한 질의의 해석:** 최초 ambiguous 관련·부분 관련 15건에는 사용자의 해석 체크가 비어 있었다. 관련도 점수와 별개로 해석별 다양성 분석에는 추가 라벨이 필요하다.

## 7. 데이터 필드와 재사용

| 필드 | 의미 |
|---|---|
| pair_id | query_id:doc_id, 문서 단독 ID로 합의하지 않음 |
| query / document | 질문 원문 / 제목·본문·메타데이터·URL 등 고정 공고 |
| score | 현재 합의 점수 0·1·2 |
| status | original_agreement / human_confirmed |
| reason / provenance | 최신 점수의 이유와 출처 |
| initial_human_* / initial_agent_* | 최초 점수·이유·검토 요청 보존 |
| requires_confirmation | v2에서는 모두 false |
| reference_date / guideline_version | 시간 기준과 규칙 버전 |

`manifest.json`에 원본 해시와 상태별 건수를 기록한다. 최초 웹 판정 DB와 독립 평가 결과는 덮어쓰지 않는다. 다른 세션은 우선 이 문서를 읽고 데이터의 상태를 확인한다. 새 합의가 생기면 이유·출처를 기록하고 새 버전을 생성한다.

새 독립 평가에는 이 문서 전체의 사례별 정답이나 과거 점수를 전달하지 않는다. 일반 규칙만 추출해 사람이 보는 것과 동일한 기업정보·조건 해석을 제공한다. 원래 120개로 기준을 조정한 뒤 같은 데이터에서 일치율이 높아졌다고 일반 성능 향상을 주장하지 않는다. 별도 표본으로 검증한다.

이 세트는 파일럿용이다. 120쌍만으로 3,022쌍 전체의 정답이나 검색 성능을 확정하지 않는다. 보류·미판정·미검수 제안을 최종 qrels에 자동으로 섞지 않는다.

### 재생성

v1은 `python RAG_evaluation/labeling/export_aligned.py`, v2는 `python RAG_evaluation/labeling/export_confirmed.py`로 재생성한다. 기존 버전과 내용이 달라지면 덮어쓰기를 거부한다. 생성에는 원본 artifacts가 필요하지만 완성된 pairs.jsonl과 이 문서는 원본 DB 없이도 읽을 수 있다.
